Where the work comes from

  • BMC Helix ITSM

    Operations raises the incident here, as they already do. Nothing about that changes.

  • Jira Cloud

    A person adds the automation label. That label is the consent — ZTO never creates its own work.

What it is allowed to look at

  • Knowledge graph

    Three months of resolved incidents, queried by rule. The same ticket returns the same evidence every time.

  • Dynatrace

    Live estate readings, pulled only when the investigation asks. Read-only, always.

How it reaches a conclusion

  • LangGraph

    Holds the investigation loop: gather, check, gather again — until there is a cause, or the budget runs out.

  • GitHub Copilot SDK

    The only model in the system. It reads the evidence pack and proposes a cause. It cannot act on it.

What it may actually change

  • Runbook registry

    The model's proposal is matched against repairs we declared. No match, no action — the ticket goes to a human with the evidence.

  • Authorisation gate

    Re-checks the runbook's own condition against a fresh estate snapshot. A stale snapshot is a refusal.

What it runs on

  • PostgreSQL 17

    One database holds the ledger, the leases and the outbox, so several servers can share the work safely.

  • OpenTelemetry / OTLP

    Its own metrics and traces, projected from the ledger and sent wherever you already look.

  • Python 3.13 · uv

    A build-time boundary check fails the build if model code ever reaches the deterministic core.

Why this shape, not another

  • Ports and adapters

    Every outside system sits behind a port, so Helix, Jira or the broker can be swapped without touching the decision logic.

  • Transactional outbox

    Reserve, send, then re-read before closing. A crash mid-write leaves a ticket duplicated in no state at all.
